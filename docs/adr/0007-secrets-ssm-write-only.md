# ADR-0007: Secrets in SSM Parameter Store, written through write-only arguments

- **Status:** Accepted
- **Date:** 2026-10-21
- **Feature:** 002-aws-deployment (research R11)

## Context

FR-022 to FR-025 cover where secrets come from, how they are stored, and where they must
never appear.

- **Source**: every secret starts as an HCP Terraform sensitive variable, or is generated by
  the infrastructure code.
- **Storage**: secrets are encrypted at rest, and each host can read only its own.
- **Never shown**: secret values must stay out of the repository, plan and apply output, and
  host logs. Where the tooling allows, they must stay out of Terraform state too.

The cost ceiling (SC-009) matters here: Secrets Manager costs $0.40 per secret per month.

## Decision

- **Store** secrets as **SSM Parameter Store `SecureString`** (standard tier, AWS-managed
  `aws/ssm` key, free), under `/rentsync/<deployment_id>/`.
- **Write** them with `aws_ssm_parameter.value_wo` and `value_wo_version`, the write-only
  arguments that need Terraform ≥ 1.11. The values never enter state or plans, and a version
  bump is what triggers a rewrite.
- **Operator-supplied secrets** (each environment's `admin_token`, the OpenObserve root
  password) are HCP sensitive variables. They are declared `sensitive = true` and
  `ephemeral = true`, so they stay out of plan files and state as well. The admin token is
  validated: at least 32 characters, and never the `.env.example` value.
- **Generated secrets** (each environment's Postgres password, the OpenObserve metadata
  database password) come from `ephemeral "random_password"`. A new value is generated every
  run, but written only when its version changes.
- **Hosts read only their own path.** Each instance role gets `ssm:GetParameter*` on its
  prefix and on the prefix's children. Environment hosts can also read the shared OpenObserve
  ingest path. `kms:Decrypt` is allowed only through SSM.
- **On the host**, `rentsync-render-env` writes a 0600 file on tmpfs (`/run/rentsync/env`). It
  never prints values, and it refuses to write a file at all if a required parameter is
  missing (`render_env_test.sh`).

## Alternatives considered

- **Secrets Manager**: built-in rotation, but it costs money per secret and needs rotation
  Lambdas this demo doesn't need. Rejected.
- **Managed `random_password` plus `value`**: simpler, but the values sit in state. Rejected.
- **Secrets in user data**: visible in the EC2 console and in state. Rejected.
- **HCP variables injected into containers directly** (for example by templating them into
  user data): the same exposure as above. Rejected.

## Consequences

- No secret value appears in the repository, state, plans or logs. A static check fails CI if
  any `SecureString` parameter sets `value`.
- **Rotation** is a variable change or version bump, then an apply, then a **reload** deploy
  (runbook §Secret rotation). The Postgres password also needs an `ALTER USER`, because the
  `postgres` image sets the password only on first initialization.
- Collectors share the OpenObserve root credentials for ingest. That is a stated trade-off;
  production would use per-environment ingest-only accounts.
- **Revisit** if automatic rotation becomes a requirement. At that point, Secrets Manager earns
  its cost.
